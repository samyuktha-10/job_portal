## 3. Bugs confirmed in this tree, ranked

### 3.1 `/notifications/` → HTTP 500
`core/views.py:1215` renders `core/notifications_list.html`. On disk the file is
`core/templates/core/notifications.html`. Probed: **500**.
Fix: rename the file or the string. (One-word change.)

### 3.2 `/control-panel/inquiries/` → HTTP 500
`core/admin_panel_views.py:91` renders `core/admin_panel/admin_inquiries_list.html`. The
`admin_panel/` folder contains `inquires_list.html` (note the misspelling), and a separate
`core/admin_inquiries_list.html` exists one level up. Probed: **500**.
Fix: point the view at `core/admin_inquiries_list.html`, or rename the file to match.

### 3.3 `/bgv/staff/verifier/step/<id>/` → HTTP 500 (blocks the verifier)
`verification/views.py:132` renders `verification/step_detail.html` — the file does not exist.
Only 4 verification templates ship: `admin_queue`, `candidate_upload`, `company_status`,
`verifier_dashboard`. Probed: **TemplateDoesNotExist**.
Impact: a verifier can see their case list but **cannot open a case**. Marking verified still
works by blind POST, which is why the loop "completed" in the probe — but there is no UI to do it.
This is the single highest-impact missing file.

### 3.4 `/bgv/company/overview/` → HTTP 500
`verification/views.py:100` renders `verification/company_overview.html` — missing. Probed:
**TemplateDoesNotExist**. This is the "all BGV requests" sidebar page.

### 3.5 No verifier login route at all
`verification/urls.py` has 8 routes and **no `staff/login/`**. `reverse('verification:verifier_login')`
raises `NoReverseMatch`. Staff views use bare `@login_required` / `@user_passes_test` with
`LOGIN_URL = '/admin/login/'` (`deploynix/settings.py:145`), so verifiers are pushed into the
**Django admin login**. Probed:

```
GET /bgv/staff/verifier/ as a plain user → 302
  redirect target: /admin/login/?next=/bgv/staff/verifier/
```

There is no `verifier_login` view in `verification/views.py` either.

### 3.6 Audit log always records `old_status == new_status`
`verification/models.py:146-162`: `self.status = status` is assigned **before**
`VerificationAuditLog.objects.create(... old_status=self.status ...)` at line 160. Probed on a
real transition: `old_status='verified' -> new_status='verified'` for a step that was `pending`.
The "immutable trail" therefore never contains a real before-value.
Fix: capture `old = self.status` at the top of `mark()` and write `old_status=old`.

### 3.7 `requirements.txt` is UTF-16 → `pip install -r` cannot parse it
First bytes are `ff fe` (UTF-16 LE BOM); every character is followed by a null byte:

```
$ python3 -c "print(open('requirements.txt','rb').read()[:4])"
b'\xff\xfea\x00'
```

Decoded, the contents are fine (18 pins, Django 5.2.16, razorpay, requests, whitenoise,
dj-database-url, psycopg2-binary, pypdf, python-decouple, pillow, gunicorn, sqlparse, tzdata,
urllib3, idna, certifi, charset-normalizer, packaging). `gunicorn==26.0.0` is **not**
platform-guarded, so a Windows `pip install -r requirements.txt` will also fail on gunicorn.
Fix: rewrite as UTF-8 and mark gunicorn `; sys_platform != "win32"`.

### 3.8 `SECRET_KEY` has no default → app will not boot without a `.env`
`deploynix/settings.py:14` is `SECRET_KEY = config('SECRET_KEY')`. Probed with the variable unset:

```
decouple.UndefinedValueError: SECRET_KEY not found. Declare it as envvar or define a default value.
```

There is no `.env` and no `.env.example` in the repo (`.env` is gitignored, correctly).

### 3.9 Job-seeker signup is fully blocked when SMTP is unconfigured
`EMAIL_BACKEND` is hard-wired to Gmail SMTP (`deploynix/settings.py:130`) with
`EMAIL_HOST_PASSWORD` defaulting to `''`. `_send_signup_otp_email` (`core/views.py:464-483`) calls
`send_mail(..., fail_silently=False)`, so a 530 makes it return `False`, and
`core/views.py:519-520` deletes the pending signup and shows "Could not send the verification
email right now." — a brand-new candidate **cannot register at all** until real SMTP creds exist.
Fix: `EMAIL_BACKEND = 'django.core.mail.backends.console.EmailBackend'` when `DEBUG`.

Probed with SMTP configured but no credentials (the state of a fresh clone):

```
OTP EMAIL ERROR: Connection unexpectedly closed
[PROBE3] http: 200
[PROBE3] User created: 0
[PROBE3] pending OTP row left behind: 0
[PROBE3] page says: True     # "Could not send the verification email right now."
```

### 3.10 Notification bell badge never updates (silent JS bug)
`core/views.py:1221` returns `{'unread_count': count}`; `core/templates/core/base.html:39-40`
reads `data.count`. Undefined > 0 is false, so the badge is permanently hidden. Endpoint itself
returns 200 (probed), which is why nothing looks broken.

### 3.11 Candidate is not notified when shortlisted
`verification/signals.py:35-36` is still the literal `# TODO: send Notification ...`. Probed:
`candidate Notification created: 0` after shortlisting.
Note the *manual* path (`request_bgv`, `verification/views.py:53-61`) **does** create the
notification with the upload link. But because the signal fires first on shortlist,
`request_bgv` always short-circuits at `verification/views.py:41-42` and that notification code is
unreachable in practice. Net effect: candidates never get told. Probed:
`request_bgv POST http (dup): 302`.

### 3.12 Live WhatsApp access token committed in plaintext
`deploynix/settings.py:147` contains a full Meta Graph API bearer token (plus phone number ID and
verify token) in a public-repo file, committed at `eea21c7`. Treat it as compromised: revoke it in
Meta Business Manager and move all three to env vars.
(`core/whatsapp/client.py` is otherwise complete and correct — it is simply never called by any
view. Verified: the only non-definition references to WhatsApp are `whatsapp_opted_in` in
models/forms/migrations.)

### 3.13 DigiLocker service would crash on first use
`verification/services/digilocker.py:15` reads `settings.DIGILOCKER_API_KEY`; that setting does
not exist anywhere (`grep -rn DIGILOCKER --include=*.py` matches only that one line). Combined
with `BASE_URL = "https://api.<your-chosen-vendor>.com/v1"`, the identity step is a stub that
raises `AttributeError` if invoked. Nothing imports it yet, so nothing breaks today.

### 3.14 Small hygiene items
- `verification/templates_snippet_applicant_row.html` is a loose snippet at the **app root**, not
  under `templates/` — it is not discoverable by any template loader and is not included anywhere.
- `verification/management/commands/create_verifier.py` does not exist in this tree, so
  `python manage.py create_verifier` is an unknown command here (matches the error you hit).
- `core/templates/core/base.html` has `{% block navbar %}` (line 23) but **no `{% block footer %}`**
  — `core/footer.html` is `{% include %}`d unconditionally near the end, so a staff page cannot
  suppress it.
- `datadump.json` contains 3 superusers: `admin` (email `admin@gmail.com`), `devisanjai` (no
  email), `admin2` (no email). The two without emails cannot use the custom panel, since
  `super_admin_login` (`core/views.py:1398`) filters on `email=..., is_superuser=True`.
- `super_admin_login` in this tree always runs the OTP path (there is no DEBUG bypass here); the
  code is printed to the terminal at `core/views.py:1417` as `[DEV] Super admin OTP for ...`, and
  the email send is `fail_silently=True`, so it degrades gracefully.
